1The big picture

This project is a timesheet and project-management web app. People log the hours they worked on a project, a manager reviews and approves those hours, and the app keeps a running record of who did what, when, and whether it's been signed off.

Like almost every modern web app, it's really two separate programs that talk to each other over the internet (even when both are running on your own computer):

🖥️ The browser-side app ("frontend")

This is what you actually see and click — the timesheet grid, the login screen, the buttons. It's plain HTML (the page structure), CSS (the colors and layout), and JavaScript (the interactivity) that your web browser downloads and runs directly. It lives in the public/ folder.

⚙️ The server-side app ("backend")

A "backend" or "server" is just a program that runs on a computer somewhere (here, your own machine during development) and waits for the browser app to ask it for things — like "log in this person" or "give me this week's hours." It's the only part allowed to talk to the database, and it's where the rules live (who can see what, who can approve what). It's built with a toolkit called NestJS and lives in the src/ folder.

Neither half can do its job alone. The frontend has no memory — refresh the page and everything it "knew" is gone unless it asks the backend again. The backend has no buttons or screens — it only responds to requests. A database (here, PostgreSQL — a program that stores structured data permanently on disk, like a very powerful spreadsheet) is the third piece: it's where every timesheet entry, user, and project actually lives between requests.

One concrete example, start to finish

Here's literally what happens when a team member clicks "Submit for review" on their weekly timesheet:

  1. The click runs a JavaScript function called submitWeek() inside public/app.js. It sends a message to the backend: "please submit my hours for the week starting July 27."
  2. That message travels over the network (even if it's just to localhost, your own machine) to an address the backend is listening on: POST /api/approvals/submit.
  3. On the backend, a file called src/approvals/approvals.controller.ts is the "door" for that address. It hands the request to a file called approvals.service.ts, which does the actual work.
  4. The service checks the database: does this person have any hours logged this week? If not, it refuses. If so, it creates (or updates) a row in a database table called Approval, marking it SUBMITTED — this is what "locks" the week from further editing.
  5. It also writes an audit-log entry (a permanent record of "who did what, when") and sends a notification to every Project Manager, so it shows up in their Inbox.
  6. The backend sends a response back saying "done." The browser app re-fetches the week's data and re-draws the screen — now showing a "Submitted" badge and no more editable boxes.

Every action in this app — logging in, logging hours, approving a week — follows this same shape: click → message to backend → backend checks the rules and touches the database → response → screen updates. Section 4 walks through three more of these in full detail.

📁 src/ — the backend (NestJS) code

NestJS is a toolkit for building backends in a very organized, repeatable way. It encourages splitting each area of functionality (projects, time entries, approvals…) into its own small folder, and each folder almost always contains the same three kinds of file:

*.controller.ts — the "door." Defines which web addresses exist (e.g. POST /approvals/submit) and which function handles each one. It does no real work itself — it just receives the request and immediately hands it off.
*.service.ts — the "worker." Contains the actual logic: checking rules, reading/writing the database, sending notifications. This is almost always the file you want when you're asking "what actually happens when X occurs?"
dto.ts ("Data Transfer Object") — describes the exact shape of data a request is allowed to send in, and validates it automatically (e.g. "email must be a valid email," "hours must be a positive number"). Bad data gets rejected before the service even runs.
*.module.ts — a short file that just lists "here is this feature's controller and service" so NestJS knows they exist. You'll rarely need to edit these except when creating a brand-new feature folder.

The feature folders in this project: auth/ (login/tokens), users/, teams/, roles/, projects/, clients/, subtasks/, assignments/, time-entries/, timesheet-rows/, approvals/, edit-requests/, notifications/, audit/, dashboards/, analytics/.

📁 prisma/ — the database blueprint and history

Prisma is the tool this project uses to talk to the PostgreSQL database without writing raw database code by hand.

schema.prisma — the "schema" is a plain-English-ish blueprint of every table in the database (Users, Projects, TimeEntries, Approvals, …) and every column each table has. Change this file when you want the database itself to store something new or different.
migrations/ — every time the schema changes, Prisma writes a small, dated file recording exactly what changed in the real database (e.g. "add this column"). This folder is a historical record, like a diary — never hand-edit an existing file in here. If you need to change the database, you edit schema.prisma and let Prisma generate a brand-new migration file for you.
seed.ts — a script that fills an empty database with realistic fake demo data (sample users, projects, weeks of timesheet history) so the app isn't blank when you first run it.

📁 scripts/ — one-off utility scripts

This folder currently has no files in it. It exists as a place for small, standalone maintenance scripts (things run by hand occasionally, not part of the running app) — for example, a one-time data-repair script. There's nothing here to run right now.

3"What does X command do?"

These are the exact shortcuts defined in this project's package.json, under "scripts". You run them by typing npm run followed by the name (a couple have no run, noted below).

CommandWhat it actually does hereWhen to use it / what you'll see
npm run build Runs nest build, which reads every TypeScript file in src/, checks it for errors, and compiles it into plain JavaScript, writing the result into dist/. Before deploying, or any time you want to double-check the backend code compiles cleanly with no errors. You'll see a short pause and then either silence (success) or a list of type errors.
npm run start:dev Starts the backend using nest start --watch — it runs the server and keeps watching every source file. Any time you save a change, it automatically rebuilds and restarts itself. This is the command you use while actively working on the backend. You'll see log lines listing every route the server registered, then Scheduling system running on http://localhost:3000.
npm run start Starts the backend once (nest start), with no auto-restart on changes. Rarely used directly — start:dev is almost always more convenient during development.
npm run start:prod Runs node dist/main — starts the already-compiled version from the dist/ folder directly, skipping any compilation step. Only works after you've run npm run build first. This is how the app would actually run in a real deployed environment.
npm run prisma:generate Runs prisma generate. Reads schema.prisma and regenerates the internal code the backend uses to talk to the database in a type-safe way (this is the "@prisma/client" library mentioned in Section 6). Run this any time schema.prisma changes, or if you get errors mentioning a database field that "doesn't exist" even though you just added it to the schema.
npm run prisma:migrate Runs prisma migrate dev. Compares schema.prisma against the real database, asks you to name the change, writes a new dated file into prisma/migrations/, and applies it to your local database immediately. Run this any time you've edited schema.prisma and want the actual database to catch up. It will prompt you in the terminal for a short name describing the change.
npm run prisma:studio Runs prisma studio — opens a visual, spreadsheet-like web page (usually at localhost:5555) where you can browse and manually edit every row in every database table. Use this when you want to look at (or quickly hand-edit) the actual data currently sitting in the database, without writing any code.
npm run db:seed Runs ts-node prisma/seed.ts directly — executes the seed script described in Section 2, wiping and refilling the database with demo users, projects, and weeks of sample timesheet data. Run this right after setting up the database for the first time, or any time you want to reset back to a clean, realistic demo state.

4How a request actually flows through the app

Three real actions in this app, traced click-by-click across both halves. This is the part that actually shows how the frontend and backend fit together — read it slowly the first time.

🔐 Flow 1 — Logging into the app

  1. You type an email and password into public/login.html and hit the login button. That page has a small <script> block at the bottom that listens for the form being submitted.
  2. The script sends a request to POST /api/auth/login, with your email and password as the message body.
  3. On the backend, src/auth/auth.controller.ts receives it at its login() function. Notice it's marked @Public() — a special marker meaning "this one endpoint doesn't require you to already be logged in," which makes sense since logging in is how you become logged in.
  4. The controller hands off to src/auth/auth.service.ts's login() function, which looks the user up in the database by email, and checks the password against a securely-hashed copy stored there (never the real password — see bcryptjs in Section 6).
  5. If it matches, the service creates a signed JWT — a tamper-proof digital token that says "this is user X, and their role is Y" — and hands back two of them: a short-lived access token and a longer-lived refresh token (used to quietly get a new access token later without forcing you to log in again).
  6. Back in the browser, the tokens and your user info are saved into sessionStorage (a small storage area tied to your browser tab), and the page redirects to app.html. From then on, every request the frontend makes includes that access token, proving who's asking.

📤 Flow 2 — Submitting a timesheet for review

  1. Inside the main app, you click "Submit for review" on your weekly timesheet. That button was drawn by a function in public/app.js and its click runs window.submitWeek().
  2. submitWeek() first does a quick, friendly sanity check entirely in the browser — it looks at which weekdays have no hours logged at all and, if any are found, asks "are you sure?" before continuing. This is just a courtesy prompt; it isn't a security rule.
  3. It then sends POST /api/approvals/submit with the week's start date.
  4. src/approvals/approvals.controller.ts receives it at submit(). Notice there's no @Roles(...) restriction on this one — any logged-in role can submit, because everyone submits their own timesheet.
  5. It hands off to approvals.service.ts's submit() function, which: checks the database for at least one logged hour that week (refuses otherwise), checks the week isn't already locked, then creates or updates a database row in the Approval table with status SUBMITTED.
  6. In the same database transaction (a group of database changes that either all succeed together or all fail together, so the data can never end up half-changed), it also writes an audit-log row and sends a notification to every Project Manager.
  7. The response comes back, and submitWeek() calls refresh(), which re-fetches the week and re-draws the table — now showing a "Submitted" badge, with editing disabled.

✅ Flow 3 — A Project Manager approving someone's hours

  1. The PM opens the Approvals inbox and clicks "Approve" next to a submitted week. That runs window.reviewApprove(userId, weekStart) in app.js.
  2. It sends POST /api/approvals/approve with the target user's ID and the week.
  3. approvals.controller.ts receives it at approve() — this one is restricted with @Roles(Role.PM), so the very first thing that happens, before any of your code even runs, is NestJS checking the requester's role from their JWT. Anyone who isn't a PM gets an automatic "forbidden" error and the request never reaches the service at all.
  4. approvals.service.ts's approve() function looks up that week's Approval row, confirms it's actually in SUBMITTED status (you can't approve something twice, or something never submitted), then — inside one transaction — marks the approval APPROVED, marks every pending time entry that week APPROVED, writes an audit-log entry, and sends a notification back to the original employee.
  5. It also recalculates that project's running hours totals (a summary table used by dashboards), so charts stay accurate without having to add up every entry from scratch every time someone looks at them.
  6. The response comes back, the Approvals inbox re-renders that row as approved, and the next time the employee loads their timesheet or notifications, they'll see it's been approved.

6What's in node_modules — direct dependencies only

node_modules will contain hundreds, maybe thousands, of folders. The overwhelming majority are indirect — things the packages below needed, which needed other things, and so on, automatically. You will essentially never open one of those by hand, and this document doesn't attempt to catalog them.
